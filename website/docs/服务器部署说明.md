# 礼账文档站服务器部署说明（审核初稿）

编写日期：2026 年 10 月 9 日。目标环境：阿里云杭州 ECS，Ubuntu 24.04，2 核 2 GB、40 GB 磁盘、3 Mbps。目标子域名：`lizhang.songisle.xyz`。

本次仅交付部署源码和实施清单。没有服务器地址、获授权的 SSH 会话、经核验的服务器主机指纹或可用的已授权 SSH agent，未登录服务器，未执行服务器更新、账户创建、防火墙修改、备案、DNS、证书申请或公网开放。阿里云环境与资源规格来自需求，尚未远端核验。

`songisle.xyz` 主站继续部署于 Cloudflare Pages。本工具不操作其项目、根域/`www` 解析或访问规则。备案通过前保持文档站在本地，或在经授权的服务器上通过回环地址和 SSH 本地隧道测试。

## 一、需要补充的连接条件

请提供操作授权范围，以及以下非秘密信息；SSH 私钥始终由用户自行管理和绑定本机 agent，不发送给协作者，也不保存于本仓库。

- 服务器公网地址或获授权的连接入口、SSH 端口、现有维护管理员用户名。
- 用户已在当前执行环境绑定并授权的 SSH agent；部署公钥 `.pub` 可以用于安装账户。
- 通过 ECS 控制台或另一可信渠道获取的 SSH 主机公钥指纹，以及核验后保存的专用 `known_hosts` 文件。不得把未经比对的 `ssh-keyscan` 输出直接当作已核验的可信主机。
- 管理员/部署人员的固定来源 CIDR，优先 IPv4 `/32` 或 IPv6 `/128`。脚本拒绝无效 CIDR、`0.0.0.0/0`、`::/0`；IPv4 最宽允许 `/24`，IPv6 最宽允许 `/64`。
- 确认安全组当前规则、已有服务和防火墙，并确认 ECS 恢复控制台可用。阿里云实名认证、备案提交、费用与安全组控制台操作另行由用户审批、执行或明确授权。

不需要阿里云主账号密码、AccessKey Secret 或 SSH 私钥。不存在上述连接条件时，不能把脚本检查结果表述为服务器部署成功。

## 二、部署结构和职责

| 位置 | 用途与权限 |
| --- | --- |
| `website/dist/` | 本地构建的纯 HTML、CSS 和静态资源；只上传此目录内产物 |
| `/usr/local/lib/lizhang-docs/` | 管理员安装的 root 所有工具，部署用户不能改写 |
| `/etc/lizhang-docs/` | root 所有的 Nginx 配置、部署用户名、初始化状态和 UFW 基线 |
| `/srv/lizhang-docs/uploads/` | 独立部署用户所有，权限 `0700`，存放发布包 |
| `/srv/lizhang-docs/site/releases/<SHA256>/public/` | 按归档摘要保存的静态版本，文件 `0444`、目录 `0555` |
| `/srv/lizhang-docs/site/releases/<SHA256>/manifest.json` | 摘要和逐文件校验清单；位于 Web 根目录之外 |
| `/srv/lizhang-docs/site/current` | 指向已验收版本的原子符号链接 |
| `/srv/lizhang-docs/site/previous` | 上一次健康版本链接，供管理员查阅 |
| `/srv/lizhang-docs/site/.nginx-validation/` | 部署用户所有，`0700`，专供无 sudo 的 Nginx 校验 PID/临时文件 |
| `lizhang-docs.service` | 独立的 Nginx 实例；备案前仅监听 `127.0.0.1:8080` |

独立部署用户没有 sudo 权限，不更改系统配置、Nginx 配置、证书或 DNS。静态更新无需重载 Nginx。初次系统准备和正式 HTTPS 配置由现有维护管理员完成。无 sudo 的校验配置使用同一份回环站点定义，但将 PID 和 HTTP 模块临时目录指向部署用户所有的独立隐藏目录，避免依赖 Nginx 默认的 root/www-data 临时路径权限；生产实例仍使用系统路径。该结构已静态审查，仍需真实 Ubuntu/Nginx 执行验收。[Nginx 临时文件路径配置](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_body_temp_path)

工具不包含广告、统计 SDK、登录或数据库，也不运行 Android 应用代码。发布包拒绝 Markdown 源文件、部署/内容/文档/脚本目录、JavaScript、隐藏文件、符号链接、硬链接、设备文件、路径逃逸和重复路径。必须包含 `index.html`、`404.html`、`robots.txt`。压缩包上限为 20 MiB，解压流为 60 MiB，静态内容为 50 MiB、5000 个归档项。SHA-256 用于校验传输内容；来源身份由获授权的 agent 和已核验的 SSH 主机密钥保障。

## 三、备案前清单

1. 审核隐私政策、用户协议、帮助内容，补齐开发者身份、联系渠道、版本和生效日期；这些文本尚未通过法律或应用商店合规审核。
2. 在本地构建、检查移动和电脑布局、页内导航、404、所有文档链接和待确认项。保留 `robots.txt` 的 `Disallow: /` 以及页面/服务器的 `noindex`。
3. 若需要服务器受限测试，先明确授权目标服务器及操作范围，获取上述连接条件。先检查运行中的服务、网络监听、已有账户和防火墙；保留管理员原会话和恢复控制台。
4. 用户在阿里云控制台审查安全组：SSH 仅允许明确来源 CIDR，关闭对公网的 80、443、8080。IPv4 和 IPv6 规则均应检查。UFW 与阿里云安全组为独立层，脚本不能验证或改动云安全组。官方提醒默认安全组可能允许全网 SSH，应按实际需要限制来源。[阿里云默认安全组说明](https://www.alibabacloud.com/help/en/ecs/user-guide/default-security-groups)
5. 经授权后，由维护管理员执行 `bootstrap.sh`；它只适合已经审查的干净专用主机，遇到既有 Nginx、80/443 监听、UFW/nftables/iptables 规则或不明管理目录会保留并停止，不能自动覆盖或放宽。既有防火墙的适配需单独审查。
6. 初始化后验证独立部署账户的新公钥 SSH 会话，以及非 root 维护管理员的新公钥会话。证明成功后才单独执行 `harden-ssh.sh`，再重复新会话验证。
7. 上传已审核的 `dist`，通过 SSH 隧道访问；确认 8080 只绑定回环、无公网 Web 监听。公网 DNS 保持现状；不签发正式证书、不开放 80/443/8080、不提交备案或付费。

### 3.1 经授权后的首次初始化

将 `website/deploy/` 源码通过已核验的 SSH 通道传至维护管理员的临时工作目录，由管理员先审查代码。此目录不会成为 Web 根目录。下面是待授权后执行的示例，示例 IP 是文档保留地址，必须替换：

```bash
sudo --preserve-env=SSH_CONNECTION bash bootstrap.sh \
  --deploy-user lizhang-deploy \
  --public-key /已审核位置/lizhang-deploy.pub \
  --admin-cidr 203.0.113.10/32 \
  --ssh-port 22 \
  --confirm-empty-dedicated-host
```

参数不使用默认 SSH 来源或默认用户名。脚本核验 Ubuntu 24.04、当前会话来源和端口；从恢复控制台执行时另传 `--console-run`。公钥只接受单行 `ssh-ed25519`；账户锁定密码，公钥使用 `from=` 限制来源，禁用 agent/X11 转发和 PTY，允许到 `127.0.0.1:8080` 的本地转发。

软件安装期间使用临时 `policy-rc.d` 阻止软件包自动启动默认 Nginx，并在退出时移除本工具创建的策略。首次新安装的 `nginx.service` 会被禁用并屏蔽，防止下次开机启动默认公网 80 端口；默认站点文件保留。本工具只启动独立 `lizhang-docs.service`。遇到既有 Nginx 时先停止整个初始化流程，保留原配置供人工评估。

默认执行 `apt-get update` 并安装 Nginx/UFW/curl/CA 证书。完整系统更新须审查维护窗口后加 `--apply-updates`；不自动重启系统，更新过程中不自动重启其他服务。看到 `/var/run/reboot-required` 时另行批准重启并检查全部服务。成功初始化后以相同账户、公钥、CIDR 和端口重复执行，会核对 UFW 基线，不会新增或放宽 SSH 规则。若中途失败形成部分状态，应先人工查明失败点，不要删除现有目录或强制重建。

### 3.2 单独执行 SSH 密钥加固

Ubuntu 建议使用 SSH 配置片段，并在生效前执行 `sshd -t`。OpenSSH 多数设置使用首次匹配值，所以脚本还检查实际生效设置，不能只看到配置文件写入就认定加固完成。[Ubuntu OpenSSH 配置说明](https://ubuntu.com/server/docs/how-to/security/openssh-server/)

从本地用新的、禁止密码和交互认证的 SSH 会话分别登录维护管理员与部署账户，并运行 `printf '%s\n' "$SSH_CONNECTION"`。其四个字段依次是客户端 IP、客户端来源端口、服务器 IP、服务器监听端口。保留原管理员会话，在最近 10 分钟内执行：

```bash
sudo bash harden-ssh.sh \
  --admin-user ubuntu \
  --admin-client-ip 203.0.113.10 --admin-client-port 新管理员会话来源端口 \
  --deploy-client-ip 203.0.113.10 --deploy-client-port 新部署会话来源端口 \
  --confirm-recovery-console
```

`ubuntu` 是示例，须改为已有且具 sudo 权限的非 root 维护账户。脚本通过服务器 `Accepted publickey` 日志核验两次新会话，不能仅靠声明“密钥已测”；缺少日志会停止。部署账户始终不加入 sudo 组。配置只关闭密码/交互认证和 root 登录，不修改端口或 `ssh.socket`。已有 `Match` 块时停止供人工审查；认证日志不使用 journald 的环境也需要人工采用等效证据。

Ubuntu 24.04 的镜像可能采用 SSH socket activation，应核查 `systemctl status ssh.socket ssh.service`；官方发行说明确认 24.04 使用 generator 从 SSH 配置生成 socket 设置。若以后要改 SSH 监听端口，必须另外审查 socket/服务、UFW、安全组和恢复方式。本阶段不改监听端口。[Ubuntu 24.04 OpenSSH 发行说明](https://documentation.ubuntu.com/release-notes/24.04/)

### 3.3 静态上传、更新与回滚

`upload-and-deploy.sh` 在 Linux/WSL 运行，需 GNU tar、Python 3、OpenSSH、`sha256sum`，使用用户已绑定的 agent。它设置 `StrictHostKeyChecking=yes`，禁止密码/交互认证和 agent 转发，不读入或上传私钥。`known_hosts` 应由可信主机指纹核验后准备。

```bash
bash website/deploy/upload-and-deploy.sh \
  --dist website/dist \
  --host 已授权服务器地址 \
  --user lizhang-deploy --port 22 \
  --known-hosts /已核验位置/lizhang_known_hosts \
  --authorized-access
```

打包按固定顺序、时间和归档所有者生成，相同产物可得到相同版本摘要。远端以独立用户加发布锁，验证归档 SHA-256 和每个条目，在专用目录解包，固定权限；先测试共享站点的 Nginx 配置，再原子切换 `current`，校验本机 HTTP 首页内容的 SHA-256。相同版本再次发布会验证原版本内容并复用。新版本健康检查失败时恢复旧链接，失败版本保留供调查。

回滚必须显式给出历史版本 SHA-256，以部署账户执行：

```bash
/usr/local/lib/lizhang-docs/rollback.sh 历史版本的64位小写SHA256
```

回滚先重新校验历史文件清单，再执行 Nginx 配置与 HTTP 内容检查。脚本不会自动清除发布包或旧版本；40 GB 磁盘应定期检查占用，清理须确认保留版本和精确目录。

### 3.4 SSH 隧道访问

```bash
ssh -F /dev/null -N -p 22 -l lizhang-deploy \
  -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -o UserKnownHostsFile=/已核验位置/lizhang_known_hosts \
  -o PreferredAuthentications=publickey -o PasswordAuthentication=no \
  -o KbdInteractiveAuthentication=no -o IdentityFile=none \
  -o ForwardAgent=no -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:8080:127.0.0.1:8080 已授权服务器地址
```

浏览器访问 `http://127.0.0.1:8080`。SSH 传输加密；本机浏览器到回环地址使用 HTTP，本阶段不能描述为已提供正式 HTTPS。不得把隧道绑定 `0.0.0.0`、使用 `-g` 或公开转发服务；手机预览优先使用本地开发预览，若扩大局域网访问须另行确认受限访问范围。

## 四、备案通过后的清单（每项待批准）

大陆服务器上的网站备案要求应在实际上线时通过阿里云备案产品核验；本说明不代替备案办理或法律判断。[阿里云备案流程](https://help.aliyun.com/en/icp-filing/basic-icp-service/user-guide/icp-filing-application-overview)

1. 用户确认网站备案已通过，确认该域名/接入商/服务器用途符合备案情况，补齐审核通过的开发者信息、联系邮箱、备案号和应展示内容。网站备案与 Android 应用备案、各商店材料应分别核查。
2. 用户批准 DNS、证书签发/相关服务费用与公网开放。只为 `lizhang.songisle.xyz` 添加或更新指向已授权 ECS 的子域解析；不操作根域、`www`、Cloudflare Pages 项目。IPv6/AAAA、Cloudflare 代理模式等在实际情况明确后单独确认，不能自行假设。
3. 管理员审查安全组与 UFW，按批准范围开放 80/443，保持 SSH 仅来自授权 CIDR，8080 仍不对公网开放。已有规则不重置。公网允许来源与 Web 对外开放由用户作最终批准。
4. 选择证书方案。仓库提供 `nginx-public-http-acme.conf.example` 作为临时 HTTP-01 验证模板，仅提供挑战路径，其余请求 404。管理员创建 `/var/lib/lizhang-acme`，以 root 安装审核后的 `/etc/lizhang-docs/public.conf`，并手动在主 `nginx.conf` 的 `http` 中增加该文件的 include，保留原 `site.conf` 回环站点。核查 IPv6 支持，按需要删去示例 IPv6 监听。先执行实际配置 `nginx -t` 再重载。
5. 根据实施当日官方安装说明安装 Certbot，确认联系邮箱和服务条款后申请证书。HTTP-01 的 webroot 验证需要公开 80 端口及正确域名解析，所以不适合本阶段提前执行。[Certbot 验证方式说明](https://eff-certbot.readthedocs.io/en/stable/using.html#webroot)
6. 得到正式证书后，管理员将 `nginx-public-https.conf.example` 审查、替换为 `public.conf`，保留回环测试配置，运行实际主配置 `nginx -t` 后重载。示例采用 TLS 1.2/1.3 和固定子域 HTTPS 跳转。证书私钥留在服务器 root 管理路径，不交给部署用户。[Nginx 配置检查说明](https://nginx.org/en/docs/switches.html)
7. 配置并验证证书自动续期以及仅针对独立实例的续期后重载，执行 `certbot renew --dry-run`。证书续期后先 `nginx -t -c /etc/lizhang-docs/nginx.conf`，再重载 `lizhang-docs.service`。不要重载被屏蔽的默认 `nginx.service`。
8. 用户审核并明确批准正式发布后，手动将 `website/site.config.json` 的 `reviewStatus` 设为 `approved`、`icpApproved` 设为严格布尔值 `true`，填写非空 `operator`、有效 `contactEmail`、有效 `YYYY-MM-DD` 格式的 `effectiveDate` 和 `icpNumber`。真实正文需先人工定稿，不能保留“审核稿”“尚未生效”“尚未通过审核”“本稿”“待确认/待填写”等状态；生成器不会自动删除这些文字或认定内容已经获批。正式域名固定为 `lizhang.songisle.xyz`。在 `website` 目录执行 `node scripts/build.mjs --public` 生成正式产物；任何页面未通过预校验都会停止并保留原产物，不得通过直接上传草稿规避。正式构建同步调整产物 `robots.txt` 和正常页面 `meta robots`，404 无审核提示但保持 `noindex,nofollow` 且没有 canonical；公开 Nginx 示例不设置全站 `noindex`，回环站点继续保留 `X-Robots-Tag: noindex`。日常静态发布仅测试不读取证书私钥的回环配置；涉及公开 TLS/系统配置的变化，必须由管理员测试实际主配置。
9. 从手机与电脑核查 HTTPS、证书链、重定向、五类页面、404、安全响应头和文档版本。核查服务器重启后只有预期实例启动、SSH 来源受限、8080 无公网监听。通过验收后再提交应用商店正式政策链接。

证书申请示例仅供获批准后的管理员实施时复核：

```bash
sudo certbot certonly --webroot -w /var/lib/lizhang-acme \
  -d lizhang.songisle.xyz --email 已确认联系邮箱 --agree-tos
sudo nginx -t -c /etc/lizhang-docs/nginx.conf
sudo systemctl reload lizhang-docs.service
sudo certbot renew --dry-run
```

证书渠道可能涉及安装方式、服务条款或费用；不要把此示例当成已获得相关批准。正式 HTTPS 模板没有被任何自动化脚本启用。

## 五、日志、备份与维护

Nginx `access_log off`，不保存站点访问日志。`error_log stderr warn` 交给该服务的 systemd journal；错误事件仍可能包含客户端 IP、请求路径等运维信息。实际日志配置、保留期限、运维联系人和删除流程待管理员确认。脚本不自动改变全局 journald 保留策略，以免影响其他服务；若需独立日志保留策略，应单独评审配置。隐私政策中不能把“关闭访问日志”写成“任何情况下均不处理 IP”。

备份对象为审核后的静态源码、root 管理配置及需保护的证书目录；使用受控备份介质，私钥不得提交 Git 或分享包。本站不接收联系人、礼金或应用备份，不能通过该站上传 Android 隐私数据。若服务器已有其他业务数据，不属于本工具清理范围。

源码交付时只具备本地检查条件：5 个 Bash 脚本的 `bash -n` 已通过（沙箱内 MSYS 权限错误后，获准以只读方式解析）；`python -B website/deploy/test_release.py` 的 15 项本地归档防护测试已通过，包括正常解包、校验清单、摘要错误、路径逃逸/绝对路径、软/硬链接、重复路径、源码/JavaScript/隐藏文件/设备文件、内容篡改、压缩炸弹及条目上限。最终源码的解析复核和站点检查完整结果以同目录交付测试报告为准。尚未在 Ubuntu 24.04、阿里云安全组、真实 SSH/agent、systemd、Nginx 或正式 HTTPS 环境完成执行验收。

后续授权环境的验收应覆盖：干净初始化与重复执行、既有服务/防火墙拒绝路径、独立账户权限、新密钥会话验证、失效 SHA 和恶意归档拒绝、同版本复用、成功发布/失败恢复/历史回滚、隧道访问、监听和公网边界，以及备案获批后的 DNS/证书/续期。只读语法或单元检查不代表这些服务器行为已验证。
