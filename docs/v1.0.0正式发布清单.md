## 批准与执行顺序

1. 本人审查 RC4 源码与分发历史。补齐运营、政策和两类独立备案/适用资料，按 [备案通过后发布步骤](备案通过后发布步骤.md) 更新正文、元数据、配置及批准记录，重新同步并计算两类内容摘要。不能只改页脚。
2. 在所有真实材料完备且本人批准后执行全量自动化和正式门禁；任何拒绝都应先纠正实际资料。候选、合成测试通过不能替代批准。
3. 最终审查通过后再按本人选定的合并方式整合 RC4 到 main，保留已整合文档站提交，不重复 cherry-pick 或 merge。本轮只提供历史方案，没有执行合并。
4. 确定签名身份与版本代码，使用干净且已提交的批准源码构建独立正式 `1.0.0`，按 [RC4 正式签名准备](RC4正式签名准备.md) 做签前检查、对齐、交互签名和签后核验。密码不能进入脚本、日志、参数或提交。
5. 完成目标设备与旧包覆盖升级验收，留存源码 SHA、签前/签后 APK 摘要、最终公共证书指纹和检查报告。跨 vivo、OPPO、未来 Play 使用兼容应用签名身份并统一版本代码台账。
6. 在备案和平台认可证明满足要求且本人另行批准后，先更新官方政策站并验证可访问链接，再提交商店；正式 GitHub Release、标签和公网部署也须在最终发布阶段授权。

## 合并方案与冻结范围

检查时 `origin/main=6493392ca6740aa7314e4e10d1c97c7931849b03`，它是 RC3/RC4 的祖先；RC3 相对 main 包含 14 个已整合提交，RC4 再增加本轮冻结提交。若 main 不前进，最终审查可选择保留全部历史的 fast-forward 或经 PR 的 merge commit；本轮不建立自动合并。若 main 前进，在后续批准的整合分支重新比较并解决冲突，重跑受影响检查，不能强推或丢弃历史。

保留全部有效 JVM、仪器和截图测试及专项设备验证入口；仅清理无引用的普通字符串、旧头像资源及已被 RC4 替代的旧验证入口。Room、备份、CSV、900ms 启动和业务页面实现没有生产代码差异。历史发布报告继续保存，但旧命令不能充当当前正式发布批准。
