## 本人批准后的内容定稿与复核顺序

1. 在另行批准的最终发布阶段，填妥三份正文和元数据；正式正文不得残留候选、尚未生效或待确认。将正式政策版本更新为本人确定的编号，保留再次告知机制。
2. 按同一批准记录填写网站主体、版本、政策版本、备案信息；批准网站全部正文及新增说明。网站公开构建仍单独执行全站定稿检查。
3. 在 `release/legal-approval.properties` 填入真实批准人、日期、APP 材料、分发历史、正式代码及证书指纹。仅记录公开信息，不写密钥路径或密码。
4. `website/` 中运行 `npm run legal:sync`，同步全文与真实批准状态；这条命令不授予批准。计算两类摘要后，将本人审阅确认的摘要记录为 `approved_content_sha256` 与 `website_content_sha256`，再同步批准镜像。
5. 执行下列检查，保留完整日志与结果。正式签名前提交已批准源码，并确认工作树干净、最终 SHA 与远端一致。

```powershell
.\scripts\legal-content-digest.ps1 | ConvertTo-Json -Depth 4
.\scripts\website-content-digest.ps1 | ConvertTo-Json -Depth 4
.\scripts\scan-unapproved-legal-content.ps1 -RequireApprovedContent
.\scripts\test-official-release-gate.ps1
# 下方代码必须替换为本人根据历史核实的数字；当前真实未批准状态下应拒绝。
.\gradlew.bat --no-daemon --console=plain '-PofficialVersionCode=24' :app:verifyOfficialReleaseContent
```

6. 使用本人确认的正式代码，完整运行 `test lint lintRelease assembleDebug assembleRelease assembleDebugAndroidTest`，并显式传入 `'-PofficialRelease=true'`、`'-PofficialVersionCode=实际获批值'`。当前候选 `23` 不是正式分发历史结论。
7. 在 `website/` 执行 `npm test`、`npm run build -- --public`，核验生成物内容与真实批准记录。单独网站测试中的真实 Android 仓库对照项会明确跳过，完整仓库则不得跳过该项。
8. 按 [签名方案](RC3正式签名操作方案.md) 核验正式未签名输入，再使用本人授权的既有身份交互签名。顺序为对齐、签名、v2/证书验证、对齐复核、最终 APK 检查、SHA-256 留档。密码不放命令行，不生成替代身份。
9. 核验 `release-verification.json`、`signing-record.json`、输入及最终 APK SHA-256、证书指纹、版本代码和源码 SHA。签名之后不再修改 APK。
10. 得到单独授权后才进行设备验收、线上网站发布、商店提交、正式 Release 或 main 合并；本轮均未执行。
