# 联系人批量管理 / 批量删除 V1

## 分支与范围

从尚未合并 main 的 `feat/contact-import-v1` 最新提交 `e31b048d0b27ef318bede94be058315f394a47b7` 创建 `feat/contact-bulk-management`。只实现多选和批量删除，不包含批量编辑、导出、分组或合并。

## 交互

正常页面顶部显示“管理”，原新增 FAB、通讯录导入、搜索、排序及详情入口保持正常行为。进入管理时默认选择为空，列表增加复选框并脱敏显示号码；点击联系人切换选择，不进入详情。顶部显示已选人数、取消和全选，底部显示取消全选及删除按钮。管理期间暂时隐藏新增、导入和底部导航，退出后恢复。

选择使用 `Set<Long>`，搜索、排序或列表刷新不改变已选 ID。“全选”追加当前可见搜索结果，保留此前隐藏的选择；“取消全选”清空全部。返回键优先退出管理，确认弹窗内先关闭弹窗，删除过程中阻止重复提交和退出。删除成功退出管理、清空选择，由 Room Flow 刷新列表；失败保留选择并显示固定中文重试提示。

## 删除安全

1. 点击删除仅请求影响预览，不删除数据。
2. 预览查询所选 ID 当前仍存在的联系人，按每位联系人统计礼金记录；显示总联系人数量、有礼金的联系人数量、礼金总条数。
3. 无礼金时显示不可恢复提示，需点击弹窗“删除”；有礼金时显示明确的永久级联删除数量，必须勾选“我确认同时永久删除 X 条礼金记录”，再点击危险样式“删除联系人及记录”。
4. 提交时在同一 Room 事务重新统计，与用户确认的逐联系人数量快照比较。任何联系人存在性或关联条数变化，均返回新预览而不删除，撤销勾选并要求重新确认。
5. 预览一致才删除 contacts，礼金交由既有 ForeignKey CASCADE 处理。不主动删除 gift_records。返回事务内实际删除联系人及礼金数量。
6. 空集合、非法或已不存在的 ID 不影响其他联系人。超过 900 个 ID 时分片，所有分片仍在同一事务；后续分片失败则整批联系人和级联礼金回滚。

快照比较的是联系人 ID 与每位关联记录数量，不包含姓名、手机号或礼金金额。用户在确认数量相同的情况下删除的是当前所选联系人的全部往来，不提供撤销。数量变化后必须重新确认，不静默扩大删除范围。

## 架构与文件

- `ContactsScreen`：管理状态、确认弹窗、明确级联勾选与成功/失败提示，只发送事件。
- `ContactsViewModel`：ID 选择、可见结果全选、预览、确认、重复点击保护和结果状态。
- `domain/model/ContactBulkDelete.kt`：影响快照、实际删除结果、需要重新确认的返回类型。
- `ContactRepository.previewDelete/deleteContacts`：业务层接口。
- `RoomContactRepository`：IO 调度并委托 DAO。
- `ContactDao`：事务统计、比较、分片删除；`ContactDeleteImpactRow` 为查询投影，不是新表。

保持 UI → ViewModel → domain.repository ← data 分层。ContactEntity、GiftRecordEntity、Room schema/版本和备份格式均不变。导入与手工创建联系人使用相同删除路径；不记录真实联系人或礼金数据。
