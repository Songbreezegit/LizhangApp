# 备案通过后发布步骤

日期：2026-10-10。当前冻结分支：`release/v1.0.0-rc4`；已验收 RC3 审查基线：`359b33626bb0d33e72ed0aa81ce214fa09ed56d6`。普通构建为 `1.0.0-rc4 / 23`。本文件是资料补齐后的操作流程，不授予政策、签名、备案、网站部署或商店提交批准。

## 当前待批准状态

网站 ICP 仍在审核，没有真实号码。`website/site.config.json` 保持 `icpApproved=false`、`reviewStatus=draft`；`release/legal-approval.properties` 的 `approval_status`、`filing_record`、`filing_status` 及 APP 材料字段保持 `pending`。审核版页脚的“ICP备案审核中”只是状态文字，不是备案号，也不链接到备案查询。正式网站及正式 App 构建继续拒绝未批准资料，不使用合成测试中的批准值。

网站备案与 APP 备案分别管理：`filing_record` / `filing_status` 对应网站公开备案资料；`app_filing_status` / `app_filing_material` 对应 APP 备案，或由目标平台明确认可的单机适用证明。获得网站 ICP 不能自动完成 APP 项；本地存储、无联网权限也不能自动取得平台认可。资料不足时继续候选审阅，不进行正式公网发布或商店提交。

## 本人最少需要完成的四组操作

1. 提供真实网站 ICP 号码和可核验的批准资料；另行提供 APP 备案材料或目标平台认可的适用证明。确认运营主体、公开联系邮箱、生效日期、正式政策版本、未成年人安排和三份完整正文。不能只提供号码就把全部其他项目标记 approved。
2. 确认全渠道实际分发历史、下一正式版本代码、最终代码审查结果及签名身份。若已有正式分发，提供历史正式 APK 或公开证书指纹，并授权复用仓库外受控密钥。若没有确定身份，先核对历史，再按 [RC4 正式签名准备](RC4正式签名准备.md) 另行确认首次创建；不自动创建密钥。
3. 审阅更新后的配置、正文、公开批准记录和两类内容摘要；明确批准本次源码 commit 与正式构建/签名。由操作人员按以下文件表同步并完成全部检查，本人无需手工改每个镜像文件。
4. 正式签名检查及另外安排的目标设备/覆盖升级验收完成后，分别授权网站上线和 vivo / OPPO 提交；后续正式 GitHub Release、main 合并及 Google Play 接入也分别执行经审查的方案。当前 RC4 工作到代码审查即停止。

密钥和最终签名输出必须位于 Git 仓库外。密码只由本人在受控本地终端交互输入，不进入脚本、属性文件、命令参数、日志、Git 或聊天。

## 收到真实资料后需要更新的文件

| 文件 | 更新内容与约束 |
| --- | --- |
| `app/src/main/assets/legal/privacy.md`、`terms.md`、`help.md` | 本人审订的完整正文、真实主体/联系方式/生效信息及适用备案资料；保留实际本地能力，不增加账号、云同步或识别宣传。 |
| `app/src/main/assets/legal/metadata.properties` | 正式政策版本、主体、邮箱、日期、网站备案资料、审核人、未成年人安排、实际审查基线及获批状态。 |
| `app/src/main/res/values*/privacy_notice.xml`、`legal_strings.xml` | 仅在批准后的告知或翻译确需变更时同步审订；全部七语言仍受摘要与扫描检查。候选专用 `candidate_release_strings.xml` 保留真实候选提示，正式 UI 不显示，仍纳入批准摘要。 |
| `release/legal-approval.properties` | 网站 `filing_record` / `filing_status`；独立 APP `app_filing_status` / `app_filing_material`；主体、日期、政策版本、审核者、批准日期、签名公共指纹、历史最大版本代码、正式代码及两个获批摘要。仅写公开批准资料，不写密钥路径或密码。 |
| `website/site.config.json` | 本人确认后设置真实 `icpNumber`、`icpApproved=true`、`reviewStatus=approved`，并同步主体、邮箱、日期、正式政策版本、`appVersion=1.0.0`、正式版本代码及实际审查基线。 |
| `website/content/{privacy,terms,help}.md`、`website/legal/` | 由 `legal:sync` 从 App 和根批准记录严格镜像；不能独立修正文或伪造批准。 |
| `website/content/faq.md`、`contact.md` | 补充经审订的实际联系渠道及说明，与规范全文一致；变化同样要求重新批准网站摘要。 |
| `website/scripts/build.mjs` | 正式页脚已从获批 `site.config.json.icpNumber` 生成并链接官方查询，无需另写号码。审核版一直保留审核状态，不能通过改页脚绕过正式构建。 |
| `store-listing/v1.0.0/` | 使用最终主体、联系方式、正式版本、官方政策/协议链接、备案/权属材料及最终包实拍截图补齐候选商店资料。 |
| `README.md`、`docs/v1.0.0正式发布清单.md`、本文件及正式验证报告 | 记录新审查提交、真实检查结果、资料批准和仍待验收事项，不覆盖历史 RC 报告中的原始证据。 |

常规 RC4 构建无需改成正式版本，也不靠改默认版本名产生正式包。正式入口保持 `-PofficialRelease=true` 加本人确认的 `-PofficialVersionCode=...`；版本代码必须高于全部实际分发历史。候选代码 23 不代表历史核实结论。

## 内容更新、摘要批准与一致性检查

在已审查工作树根目录执行。先定稿真实正文、元数据、网站配置和公开批准字段；两类摘要最后计算。下面命令只镜像和核对，不授予批准。

```powershell
$ErrorActionPreference = 'Stop'
& node .\website\scripts\legal-consistency.mjs --sync
if ($LASTEXITCODE -ne 0) { throw '镜像同步失败，停止发布。' }
.\scripts\legal-content-digest.ps1 | ConvertTo-Json -Depth 4
.\scripts\website-content-digest.ps1 | ConvertTo-Json -Depth 4
```

本人审阅实际内容后，将批准的法律摘要写入根批准文件 `approved_content_sha256`，将批准的网站摘要写入 `website_content_sha256`。前者覆盖三正文、元数据和七语言告知/候选资源（当前 25 输入）；后者覆盖网站全部 Markdown 正文和 `site.config.json`（当前 6 输入）。批准文件本身不参与摘要，更新摘要字段后再同步批准镜像；不能复制测试 fixture 的摘要或把 `pending` 机械替换为 `approved`。

```powershell
& node .\website\scripts\legal-consistency.mjs --sync
if ($LASTEXITCODE -ne 0) { throw '批准镜像同步失败。' }
& node .\website\scripts\legal-consistency.mjs
if ($LASTEXITCODE -ne 0) { throw 'App 与网站正文或批准资料不一致。' }
.\scripts\scan-unapproved-legal-content.ps1 -RequireApprovedContent
.\scripts\test-official-release-gate.ps1
if ($LASTEXITCODE -ne 0) { throw '正式门禁回归失败。' }
```

变更任何正文、告知/翻译、元数据、网站配置或 FAQ/contact 后，重新计算并由本人批准相应摘要；只修改网页显示文字会被摘要或配置匹配检查拒绝。“ICP备案审核中”即使与批准文件同步，也不能作为正式号码通过门禁。合成通过/拒绝样例只验证门禁代码，不是现实备案或政策批准。

## 完整检查与发布顺序

1. 保存并审查批准资料、变更文件清单、两类摘要及全渠道版本台账；提交最终源码并核对远端 SHA。合并方案先审查，不擅自合并 `main`。
2. 运行完整 Android 检查。Windows 构建使用项目内 TEMP/TMP 和 JDK UnixDomainSocket 临时目录，避免修改全局环境；JDK 17 和项目既有 SDK 配置不变。

```powershell
$releaseTemp = Join-Path (Get-Location) 'build\official-check\tmp'
New-Item -ItemType Directory -Path $releaseTemp -Force | Out-Null
$env:TEMP = $releaseTemp
$env:TMP = $releaseTemp
$env:JAVA_TOOL_OPTIONS = '-Djdk.net.unixdomain.tmpdir=' + $releaseTemp
$officialCode = Read-Host '本人根据各渠道实际分发历史批准的正式版本代码'
if ($officialCode -notmatch '^[1-9][0-9]*$') { throw '正式版本代码须为本人确认的正整数。' }
$officialCodeArgument = '-PofficialVersionCode=' + $officialCode
& .\gradlew.bat --continue --no-daemon --console=plain --max-workers=1 '-Pkotlin.compiler.execution.strategy=in-process' '-PofficialRelease=true' $officialCodeArgument test lint lintRelease assembleDebug assembleRelease assembleDebugAndroidTest :app:verifyLegalContentConsistency :app:printLegalContentDigest
if ($LASTEXITCODE -ne 0) { throw '正式内容门禁或 Android 检查失败，停止签名。' }
```

3. 网站全测试和正式构建在完整仓库中运行，不跳过真实 Android 对照。`--public` 必须成功；候选 build 的成功不能代替此项。

```powershell
Push-Location website
try {
    & npm.cmd test
    if ($LASTEXITCODE -ne 0) { throw '网站测试失败。' }
    & npm.cmd run legal:check
    if ($LASTEXITCODE -ne 0) { throw '网站一致性检查失败。' }
    & npm.cmd run build -- --public
    if ($LASTEXITCODE -ne 0) { throw '正式网站构建拒绝，停止上线。' }
} finally { Pop-Location }
git diff --check
if ($LASTEXITCODE -ne 0) { throw 'Git 差异检查失败。' }
```

4. 按 [RC4 正式签名准备](RC4正式签名准备.md) 对正式未签名 APK 完成签前检查，使用本人授权的既有仓库外密钥交互签名；先对齐，再签名，再验证证书、v2、页对齐、版本/包名/权限/调试组件/法律绑定与最终 SHA-256。失败立即停止，不发布遗留文件；不得为生成正式 APK 暂时降低门禁。
5. 另行完成实体目标设备、首次隐私告知/拒绝/重试、旧正式包覆盖升级与数据保留、通知、导出及备份恢复验收。RC4 仅编译仪器 APK，设备执行为 0 项；自动化结果不能替代这些实际验收。
6. 本人另行授权后才能公开上线获批网站 `dist/`，核验 HTTPS、可访问性、真实备案号与当前正文摘要。正式商店提交必须等待官方隐私政策和用户协议可访问及网站/APP 两类材料符合目标平台审核要求。
7. 使用同一包名和经本人确认的应用签名身份提交 vivo / OPPO；按交付目录补齐截图和证明。未来 Google Play 的应用签名密钥、上传密钥和托管流程按届时官方要求另行审查，避免造成跨渠道更新身份不一致。
8. 根据最终授权执行正式 GitHub Release、main 合并或渠道发布，记录 APK、公开证书、版本代码、最终源码 SHA、两类内容摘要及审核结果；任何后续内容变化重新走批准和检查。

当前不操作 Cloudflare、ECS、DNS、线上网站、商店或正式 GitHub Release。没有真实备案号及独立 APP 适用资料、政策主体/日期和签名身份批准前，上述正式步骤保持阻止。
